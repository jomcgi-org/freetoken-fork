### Root cause

The dominant problem was verify routing, not snapshot bandwidth.

The scheduler changed each width-4 MTP window from `decode` to `prefill`. This caused all target-model layers to use extend machinery and routed every offloaded MoE layer through `_prefill_routed`, including the nine DISK layers and their prefill staging.

Snapshot size at TP=1:

| State | Shape per request | Bytes |
|---|---:|---:|
| GDN convolution | `[36, 10240, 3]`, bf16 | 2,211,840 |
| GDN recurrent | `[36, 48, 128, 128]`, fp32 | 113,246,208 |
| PLE convolution | `[1, 10240, 9]`, bf16 | 184,320 |
| PLE n-gram | `[1, 2]`, int32 | 8 |
| QSA pending ring | `[12, 8, 128]`, bf16 | 24,576 |
| Total | | 115,666,952 bytes, 110.309 MiB |

The full-attention head dimension is 256, but the shipping GDN key/value dimensions are 128.

A rejected window previously moved up to 220.6 MiB through clone plus restore. The exact-shape CPU benchmark measured:

```text
run=2 save_us=5347 restore_us=2335 aggregate_GiB_s=28.05
run=3 save_us=5502 restore_us=2105 aggregate_GiB_s=28.32
```

Attributing the entire 12.4 seconds to that traffic would imply only 0.0187 GB/s, which is not credible. Snapshotting was measurable but not the root cause.

### Fix

- Width-4 cache space is reserved while the batch stays classified as decode.
- Target verification runs ordered width-1 eager decode operations.
- Verification stops at the first mismatch, leaving GDN, PLE, QSA, and KV state exactly at the committed prefix.
- No state snapshot or rollback is performed, including on full acceptance.
- Offloaded MoE now sees decode routing instead of DISK prefill staging.
- With 31.7% independent acceptance, the expected target steps per window are approximately `1 + p + p² + p³ = 1.45`.

Main implementation: [engine.py](/Users/jomcgi/repos/FreeToken/python/freetoken/engine/engine.py:1145), [scheduler.py](/Users/jomcgi/repos/FreeToken/python/freetoken/scheduler/scheduler.py:854), and [spec_decode.py](/Users/jomcgi/repos/FreeToken/python/freetoken/spec_decode.py:13).

### Instrumentation

Each MTP window now logs asynchronously measured CUDA timings:

```text
MTP verify window, route: decode, width: 4, accepted: 1, verify_us: 2300, snapshot_us: 0, draft_us: 700
```

That is the CPU formatting smoke-test output. The reported pre-change baseline had no phase timing fields:

```text
Decode batch, ... gen throughput (token/s): 0.24, ... acceptance rate: 0.3170
```

A production after-measurement requires rerunning on the configured GPU server. `snapshot_us` will remain zero by design.
